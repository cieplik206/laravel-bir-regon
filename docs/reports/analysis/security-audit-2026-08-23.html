Podsumowanie wykonawcze

W audytowanym stanie nie wykryto podatności krytycznej, złośliwego kodu, rzeczywistego sekretu w repozytorium ani znanego advisory w zainstalowanym grafie 83 zależności runtime. Pakiet nie ma także bezpośrednich sinków SQL, shell, systemu plików lub szablonów, a użytkownik nie może sterować adresem endpointu SOAP.

Werdykt dla stanu bazowego: nie wykonywać kolejnego wydania ani composer install/update na stacji maintenera przed zamknięciem punktów P0. Kod runtime wymaga wydania bezpieczeństwa przede wszystkim z powodu potwierdzonego ujawniania klucza BIR w łańcuchu wyjątków i możliwości umieszczenia klucza w payloadzie kolejki przez serializację buildera.

Aktualizacja remediacji: H-01 zamknięto przez aktualizację Composera do 2.10.2 i konfigurację kluczy podpisów. H-03 zamknięto przez zredagowaną translację wyjątków, bezpieczną przyczynę zastępczą oraz testy regresyjne uruchamiane także przy zend.exception_ignore_args=0. Zakres i ograniczenia

W zakresie

  • Całe śledzone src/, config/, testy i publiczne API pakietu.
  • Zainstalowane gusapi/gusapi 6.3.2, szczególnie SOAP, WSDL, sesja, SimpleXML i dekodery raportów.
  • composer.json, lokalny ignorowany composer.lock, 141 pakietów runtime i dev oraz lokalne narzędzie Composer.
  • Laravel ServiceProvider, facade, cykl życia singletonów i konfiguracja sekretów.
  • GitHub Actions, publiczne ustawienia ochrony gałęzi/rulesets, tagi i wydania.
  • 69 śledzonych plików, 10 osiągalnych commitów i 146 lokalnych blobów Git pod kątem sekretów.
  • Dokumentacja, SECURITY.md i skill Laravel Boost.

Poza zakresem lub bez pełnego dostępu

  • Wewnętrzna implementacja i infrastruktura serwera GUS.
  • Produkcyjne aplikacje konsumentów, ich kontrolery, rate limiting, logi i kolejki.
  • Prywatne ustawienia GitHub wymagające uprawnień administratora, w tym status Dependabot Security Updates, 2FA, tokeny Packagist i lista współpracowników.
  • Penetracja produkcyjnego endpointu GUS; wykonano tylko dokumentowane testy sandbox.
  • Bezpieczeństwo hosta, systemu operacyjnego, Redis/SQS i konfiguracji PHP konsumenta.

Wyniki zależne od czasu — advisories, wersje pakietów i publiczne ustawienia GitHub — są aktualne na 23 sierpnia 2026. Lokalny runtime: PHP 8.4.19, libxml 2.9.13, OpenSSL 3.6.1.

High Pewność wysoka Status: naprawione

H-01 — podatny lokalny Composer 2.9.5

composer diagnose potwierdził sześć aktywnych advisory dotyczących binarki używanej na stacji audytowej. Naprawiona, aktualna wersja to 2.10.2. Problem nie jest zależnością runtime pakietu, ale dotyczy narzędzia, które instaluje i aktualizuje cały graf kodu.

Remediacja: lokalny Composer został zaktualizowany do 2.10.2, klucze podpisów zostały skonfigurowane, a composer diagnose i composer audit przechodzą.

CVE / GHSA Poziom Skutek
CVE-2026-59948 High Zapis pliku poza vendor/ przez złośliwą nazwę pakietu.
CVE-2026-45793 High Ujawnienie GITHUB_TOKEN w logach Actions.
CVE-2026-40261 High Command injection przez złośliwy URL/reference Perforce.
CVE-2026-40176 High Command injection przez złośliwą definicję repozytorium Perforce.
CVE-2026-59946 Medium Path traversal w polu bin i chmod pliku hosta.
CVE-2026-59947 Medium Ujawnienie danych HTTP Basic/PAT w verbose logs.

Repozytorium nie definiuje Perforce ani własnych repozytoriów Composer, więc dwa wektory P4 mają mniejszą ekspozycję. Nie zmniejsza to pilności aktualizacji, ponieważ kolejne composer update wykonuje zewnętrzny kod i może spotkać nowy lub skompromitowany pakiet.

Naprawa

  1. Przed kolejnym install/update wykonać brew upgrade composer.
  2. Potwierdzić composer --version ≥ 2.10.2 i ponowić composer diagnose.
  3. W CI wymusić bezpieczny minimalny patch, a nie ogólne composer:v2.
  4. Jeżeli używany jest composer self-update, skonfigurować klucze podpisu; Homebrew ma własny kanał aktualizacji.
High Pewność wysoka

H-02 — brak technicznie wymuszonej integralności gałęzi i wydań

Publiczne GitHub API zwraca protected: false dla main, a endpoint rulesets zwraca pustą listę. Osoba lub token z uprawnieniem write może ominąć PR i CI, wykonać force-push albo zmienić workflow. Instrukcja „release only after CI passes” istnieje wyłącznie jako proces tekstowy.

Ryzyko nie jest hipotetyczne: tag v1.0.2 utworzono 2026-08-23T00:37:47Z, natomiast CI dla tego SHA zakończyło się o 00:38:18Z. Tag powstał 31 sekund przed wynikiem testów. Obecne tagi są annotated, lecz niepodpisane; wydania GitHub nie są immutable, a dla v1.0.1 i v1.0.2 nie ma odpowiadających GitHub Releases.

Naprawa

  • Ruleset main: wymagany PR, co najmniej jedno approval, rozwiązane rozmowy, required status CI Passed, blokada force-push i delete, bez administracyjnego bypassu w zwykłym procesie.
  • CODEOWNERS dla .github/workflows/**, composer.json, .gitignore, kodu transportu i plików release.
  • Osobny ruleset v*, który ogranicza create/update/delete tagów do roli lub bota wydawniczego.
  • Release workflow publikuje wyłącznie SHA z chronionego main po wymaganym CI; podpisane tagi, immutable releases, SBOM i provenance/checksum.

Dowody publiczne: status gałęzi oraz rulesets.

High Pewność wysoka Status: naprawione

H-03 — klucz BIR i SID wyciekały przez łańcuch wyjątków i trace

Stan bazowy: Zależność gusapi/gusapi 6.3.2 wpisuje pełny klucz użytkownika do komunikatu InvalidUserKeyException. Pakiet zmieniał komunikat główny na bezpieczne Invalid API key, ale zachowywał surowy wyjątek jako previous. Laravel/Monolog normalizuje łańcuch przyczyn, a dokumentacja pakietu wprost zaleca report($exception) i informuje, że przyczyna jest dostępna przez getPrevious().

  • src/BirClient.php w stanie bazowym — zachowanie secret-bearing cause.
  • GusApi.php:65–73 — klucz w komunikacie upstream.
  • docs/error-handling.md w stanie bazowym — rekomendowane raportowanie pełnego wyjątku.

Dodatkowe kanały: przy zend.exception_ignore_args=0 błąd WSDL/TLS może ujawnić aktywny klucz w argumentach make() lub konstruktora GusApi; błąd transportu po zalogowaniu może ujawnić SID w trace. Lokalna konfiguracja miała zend.exception_ignore_args=Off. 

public message: Invalid API key
stringified exception / Monolog: sentinel-present

Remediacja: BirClient redaguje aktywny klucz i SID, po czym kończy ramkę przyjmującą surowy Throwable. Nowy łańcuch wyjątków jest budowany wyłącznie z bezpiecznych wartości skalarnych: oczyszczonego komunikatu i oryginalnego kodu błędu. getPrevious() zachowuje bezpieczny BirException, ale nie surowy obiekt upstream. Callbacki operacji są statyczne i nie wiążą ani nie przechwytują instancji klienta. Testy canary sprawdzają message, previous, string i argumenty trace, a przez refleksję odrzucają closure związane z BirClient lub przechwytujące go w zmiennych statycznych. Regresja działa również przy zend.exception_ignore_args=0.

Wpływ

Pełny klucz może trafić do storage/logs, Sentry/APM, outputu debug, transkryptu wsparcia lub centralnego systemu logów. Wartość odrzucona przez GUS może być już nieważna, lecz ten sam kanał trace dotyczy także prawidłowego klucza przy awarii inicjalizacji transportu.

Naprawa

  1. Status: zrobione Dla InvalidUserKeyException zachować najwyżej zredagowaną przyczynę zastępczą, nigdy oryginalny obiekt zawierający credential.
  2. Zgłosić upstream i usunąć klucz z komunikatu w gusapi; oznaczyć klucz, SID i surowy request przez #[\SensitiveParameter].
  3. Nie kopiować surowych komunikatów transportu do publicznych wyjątków; zastosować stabilne kody i bezpieczną diagnostykę.
  4. Ustawić zend.exception_ignore_args=On w produkcji jako obronę dodatkową, nie zamiast redakcji kodu.
  5. Przeszukać istniejące logi pod kątem komunikatu upstream i obrócić każdy klucz, który mógł zostać utrwalony.

Ustalenia średnie

Medium Pewność wysoka

M-01 — serializacja buildera lub usługi ujawnia klucz API

BirRequestBuilder przechowuje klienta, a BirClient przechowuje surowy $apiKey. Klasy nie blokują natywnej serializacji. Potwierdzony test serialize($service->forNip(...)) zawierał pełny syntetyczny klucz. 

serialize(builder) → sentinel-present

Builder lub serwis zapisany jako property Laravel joba może umieścić klucz w domyślnie niezaszyfrowanym payloadzie database/Redis/SQS, backupie i narzędziu obserwowalności. Po zainicjalizowaniu SOAP serializacja może zamiast tego zakończyć się błędem, co nie usuwa kanału przed pierwszym wywołaniem.

Naprawa

  • Jawnie zabronić serializacji BirClient, BirRegonService i builderów.
  • Job przechowuje tylko typ operacji i identyfikator; serwis rozwiązuje w handle().
  • Dodać test natywnej serializacji i test typowego queue job z wartością canary.
Medium Pewność wysoka

M-02 — repozytorium nie ignoruje plików .env

.gitignore zawiera tylko artefakty vendor/test/build i composer.lock. Jednocześnie README, dokumentacja instalacji i skill Boost instruują zapisanie BIR_API_KEY w .env. Przypadkowe git add . może więc śledzić credential.

Skan obecnego drzewa, osiągalnej historii, reflogu i lokalnych nieosiągalnych blobów nie znalazł rzeczywistego sekretu. Jest to brak kontroli prewencyjnej, a nie stwierdzony incydent.

Naprawa

/.env
/.env.*
!/.env.example

Dodać skan sekretów w pre-commit/CI oraz ochronę typowych plików z kluczami, logów i lokalnych credential stores. Publiczny klucz sandbox nie jest sekretem.

Medium Pewność wysoka

M-03 — brak walidacji pozwala ominąć limit batch i wzmacnia nadużycia

Publiczne metody przyjmują dowolny string, a typ elementów batcha istnieje tylko w PHPDoc. Nie ma kontroli cyfr ASCII, długości, pustki, przecinków, znaków sterujących ani całkowitego rozmiaru. Zależność liczy elementy tablicy, a potem skleja je przecinkiem. Jeden element zawierający 26 wartości przechodzi kontrolę jako batch rozmiaru 1, lecz tworzy 26 identyfikatorów protokołu. 

array-elements=1 protocol-identifiers=26

To delimiter injection, nie klasyczny XML injection — wartości koduje SoapClient. Pozwala jednak ominąć limit 20, zwiększyć request/response i obejść limity aplikacji liczone per element. Batch >20 jest odrzucany dopiero po logowaniu; nie-string może wyrzucić surowy Error przed mapowaniem do hierarchii BirException. Facade może też skalarne liczby koercyjnie zamienić na string, tracąc zera wiodące.

Naprawa przed factory/login

  • NIP i KRS: dokładnie 10 cyfr ASCII.
  • REGON: 9 lub 14 cyfr zgodnie z wybraną metodą.
  • Batch: prawdziwa lista stringów, maksymalnie 20, bez separatorów/control chars.
  • Limit bajtów i liczby elementów; opcjonalna suma kontrolna oraz deduplikacja.
  • Jednolity, typowany wyjątek walidacji bez zdalnego requestu.

Wprowadzenie ścisłej walidacji zawęża zachowanie publiczne. Dokumentacja już określa formaty cyfrowe, ale przed wydaniem należy ocenić wpływ SemVer i opisać zmianę w changelogu oraz skillu Boost.

Medium warunkowe Pewność wysoka

M-04 — brak konfigurowalnego deadline i amplifikacja timeoutów

Builder gusapi nie ustawia connection_timeout, timeoutu odczytu ani całościowego budżetu operacji. Dziedziczy globalny default_socket_timeout (60 s w środowisku audytu). Po wielu błędach, w tym not-found reprezentowanym wyjątkiem, klient wykonuje dodatkowe zdalne isLogged(). Awaria może więc zużyć kilka osobnych okien timeoutu na jedno wywołanie aplikacyjne.

Wykorzystanie wymaga, by konsument wystawił operację publicznie i nie ograniczał ruchu. Podczas spowolnienia GUS napastnik może wyczerpać pulę workerów przez wiele równoległych, nawet poprawnych zapytań.

Naprawa

  • Konfigurowalne connect/read timeouty oraz jeden overall deadline obejmujący recovery.
  • Nie wykonywać session probe po jednoznacznym DNS/TLS/timeout i po lokalnej walidacji.
  • W aplikacji konsumującej: throttle per użytkownik/IP, cache wyników, concurrency limit i circuit breaker.
  • Testy z kontrolowanym lokalnym transportem i zegarem, bez realnego oczekiwania.

PHP rozróżnia timeout połączenia od limitu oczekiwania na wolną odpowiedź; opisuje to oficjalna dokumentacja SoapClient.

Medium warunkowe Pewność wysoka

M-05 — nieograniczony XML/response i ekspansja encji powodują memory DoS

Trzy dekodery gusapi 6.3.2 tworzą new SimpleXMLElement($raw) bez odrzucenia DOCTYPE, limitu rozmiaru, głębokości, elementów lub łącznej długości tekstu. Dodatkowo MultipartResponseDecoder kopiuje pełne body, trace=true zachowuje ostatni request/response, a wynik jest materializowany w tablicach.

Kontrolowany, lokalny test decoderem pełnego raportu rozwinął 100 676 B XML do wartości 10 000 000 B, zwiększając peak memory o około 10 MB. Nie potwierdzono odczytu pliku przez klasyczne XXE na lokalnych domyślnych ustawieniach; brak LIBXML_NOENT ogranicza ten wariant. Problemem pozostaje wewnętrzna ekspansja encji i ogólny brak bounds. 

input-bytes=100676 output-bytes=10000000 peak-delta=10010624

Endpointy są stałe, używają HTTPS i nie wyłączają weryfikacji certyfikatu. Exploit wymaga więc skompromitowanego/złośliwego GUS lub innego naruszenia zaufanego kanału. Przypadkowo nadmierny raport zbiorczy może wywołać podobny skutek bez przeciwnika.

Naprawa upstream lub bezpieczny fork

  • Odrzucić każdy DOCTYPE przed parsowaniem oraz wyłączyć sieć przez LIBXML_NONET.
  • Użyć LIBXML_NO_XXE, gdy platforma go udostępnia, bez włączania substytucji encji.
  • Wymusić maksymalny rozmiar raw XML, liczbę rekordów, głębokość i łączny rozmiar tekstu.
  • Wyłączyć trace domyślnie; dla bulk rozważyć streaming/chunking lub twardy limit.
  • Dodać hostile fixtures: entity expansion, deep nesting, ogromny text node i malformed XML.

Oficjalne znaczenie flag libxml opisuje manual PHP.

Medium warunkowe Pewność średnio-wysoka

M-06 — stanowy singleton nie jest concurrency-safe

ServiceProvider rejestruje klienta i usługę jako singletony. Klient współdzieli mutowalne $api, $loggedIn, SID i stream context, a recovery resetuje te pola bez synchronizacji. Dwa równoległe Fibery/coroutines w tym samym kontenerze mogą równocześnie logować, resetować świeży klient lub nadpisywać stan diagnostyczny.

Sekwencyjny PHP-FPM jest bezpieczny w tym modelu. Ryzyko dotyczy Octane, faktycznie współbieżnych workerów oraz dynamicznej konfiguracji per tenant. Długowieczny singleton zatrzymuje również stary klucz po rotacji do czasu restartu procesu.

Naprawa

  • Rozważyć scoped() dla klienta i usługi, pozostawiając bezstanową fabrykę singletonem.
  • Alternatywnie zapewnić osobną instancję per równoległa operacja albo synchronizację login/call/recovery.
  • Udokumentować brak thread-safety i obowiązek restartu Octane/Horizon/queue po rotacji klucza.
  • Dodać deterministyczne testy interleavingu z Fiberami.
Medium Pewność wysoka

M-07 — GitHub Actions są przypięte do mutowalnych tagów

Oba workflowy używają actions/checkout@v5 i shivammathur/setup-php@v2. Zmiana lub przejęcie tagu upstream zmienia wykonywany kod bez diffa w tym repozytorium. Checkout domyślnie pozostawia credential dostępny dla kolejnych kroków.

Wpływ ogranicza jawne permissions: contents: read, publiczny kod, brak sekretów/publish joba oraz brak pull_request_target.

Naprawa

  • Pełne, zweryfikowane 40-znakowe SHA każdej akcji z komentarzem wersji.
  • persist-credentials: false we wszystkich checkoutach.
  • Dependabot dla ekosystemu github-actions.
  • Jawna bezpieczna wersja Composer ≥2.10.2 w setup-php.
Medium Pewność wysoka

M-08 — brak reprodukowalnego i cyklicznego gate zależności

composer.lock jest ignorowany, a wszystkie joby wykonują composer update. Każdy build może więc pobrać i uruchomić nową zgodną wersję przed review; dozwolony plugin Pest wykonuje kod podczas instalacji. composer audit działa dopiero po instalacji i tylko dla jednego grafu quality, nie dla wszystkich wariantów Laravel/lowest/highest.

Dla biblioteki floating matrix jest uzasadniony testowaniem zgodności. Brakuje jednak jednego recenzowanego baseline i okresowego sygnału dla nowych advisory. Brak .github/dependabot.yml; audit uruchamia się tylko po push/PR. Lokalny ignorowany lock wygenerowany na PHP 8.4 nie jest instalowalny na deklarowanym PHP 8.3, więc nie może zostać bezpośrednio przyjęty jako baseline.

Naprawa

  • Zachować floating lowest/latest matrix, ale dodać jeden job z recenzowanym lockiem dla PHP 8.3.
  • Najpierw resolve bez install/scripts/plugins, następnie audit locka, dopiero potem wykonanie zależności.
  • Audit każdego unikalnego grafu, szczególnie prefer-lowest; Composer ≥2.10.2 z policy blocking.
  • Dependabot dla Composer i Actions oraz cykliczny workflow security.

Ustalenia niskie

Low Pewność wysoka

L-01 — surowe identyfikatory i komunikaty w logach

BirNotFoundException interpoluje pełny NIP/REGON/KRS, a batch skleja całą listę. Wartość z CR/LF tworzy dodatkową linię komunikatu; bardzo długi identyfikator powiększa log. Dokumentacja dodatkowo loguje surowy $diagnostics->message pochodzący z zewnętrznej usługi. 

Nie znaleziono firmy dla NIP: 123
[ALERT] forged

Walidacja z M-03 usuwa kontrolne znaki, ale nadal warto maskować/trunkować identyfikator, ograniczyć długość upstream message i logować bezpieczne pola strukturalne. Wyniki GUS należy traktować jako niezaufany tekst i escape’ować przy renderowaniu; część danych rejestrowych może dotyczyć osób fizycznych.

Low Pewność wysoka

L-02 — security decorator klienta nie obejmuje sandboxa

Produkcja korzysta z bindingu BirClientInterface, ale sandbox jest tworzony wprost przez new BirClient(...). Fake blokujący sieć, rate limiter lub decorator polityki podpięty do interfejsu jest pomijany po BirRegon::sandbox(). Dokumentacja częściowo to ujawnia, lecz guidance testowe zbyt szeroko obiecuje brak przypadkowych requestów.

Dodać osobny binding/fabrykę klienta sandbox lub jawny mechanizm wyłączenia sandboxa w produkcji; zaktualizować dokumentację testów.

Low Pewność wysoka

L-03 — wynik login() === false jest ignorowany

ensureLoggedIn() ustawia $loggedIn=true bez sprawdzenia bool zwróconego przez GusApi::login(). Kontrolowany fake zwracający false nadal wykonał wyszukiwanie. Bieżące gusapi 6.3.2 zawsze zwraca true albo rzuca, więc nie ma dziś bezpośredniego exploita; jest to brak fail-closed wobec alternatywnej fabryki lub zmiany zależności.

Wymagać jawnego true, w przeciwnym razie rzucać zredagowany BirAuthenticationException i nie wykonywać operacji biznesowej.

Low Pewność wysoka

L-04 — testy dają niepełne assurance na granicy SOAP/XML/TLS

Lokalne fake’i zwracają już zdekodowane obiekty i omijają factory, WSDL, TLS, nagłówek SID, SimpleXML, limity transportu oraz sekret w upstream exception. Testy recovery używają fabryki zwracającej ten sam obiekt, więc dwa logowania nie dowodzą utworzenia świeżego klienta. Domyślna konfiguracja tylko wyklucza grupę sandbox; nie blokuje technicznie egressu. Coverage nie ma skonfigurowanego <source>, a CI go nie mierzy.

Dodać deterministyczne contract tests na lokalnym/fake transport layer, hostile XML fixtures, secret canary w formatterze Monolog, sequence factory, fuzz/property tests wejść, mutation tests auth/retry i uruchamianie zwykłego suite w środowisku bez egressu.

Kontrole pozytywne

  • Brak rzeczywistych sekretów w śledzonych plikach i lokalnej historii Git.
  • 0 aktualnych advisory i 0 porzuconych pakietów w grafie runtime/dev lock.
  • gusapi/gusapi 6.3.2 jest najnowszą wersją Packagist i ma 0 opublikowanych advisory.
  • Endpointy prod/test są stałe, używają HTTPS, a kod nie wyłącza verify peer/name.
  • Nie potwierdzono SSRF sterowanego wejściem, SQL/command/template injection ani unsafe PHP deserialization gadget.
  • Nie potwierdzono klasycznego XXE z odczytem pliku; problem XML dotyczy bounds/entity expansion.
  • Production i sandbox mają osobne instancje, klucze, sesje i zamknięty enum środowiska.
  • Pusty klucz produkcyjny kończy operacje uwierzytelnione fail-closed przed SOAP.
  • Typy raportów są enumami, więc konsument nie wstrzykuje dowolnej nazwy raportu.
  • Retry jest ograniczony do jednej próby i dotyczy operacji odczytowych.
  • Pusty batch zwraca pusty wynik bez requestu.
  • CI ma minimalne contents: read, limity czasu i brak niebezpiecznego pull_request_target.
  • Composer ma zamkniętą allowlistę jednego pluginu dev i nie ma hooków install/update.
  • SECURITY.md wskazuje prywatne raportowanie i prawidłowo zabrania publikowania kluczy.
  • Pełna jakość lokalna oraz bieżący kontrakt z publicznym sandboxem GUS przechodzą.
